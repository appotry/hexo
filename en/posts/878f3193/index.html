This article covers all 16 markdown-it plugins enabled by the theme. Every plugin follows the same learning path: minimal example → common variants → all syntax forms → parameters & options → boundaries & pitfalls. All examples appear as pairs — effect first, source after — so whatever you see, you immediately know how it was written.

Plugin registration lives in markdown.plugins of the root _config.yml; render options (breaks / linkify / typographer / html) live in markdown.render of the same file.

2.2 Common variants

2.4 Parameters & options

  • The definition-line format is fixed: *[abbr]: full name; a space after the colon is allowed

2.6 Summary

  • Keep the definition line on a line of its own; never squeeze it into the body
  • Case-sensitive: HTML ≠ html
  • Putting the definitions at the end of the file is fine — position does not matter

3. footnote (markdown-it-footnote)

3.1 Minimal example

3.2 Common variants

Corresponding source:

Corresponding source:

3.3 All syntax forms

FormRenderNotes
正文[^1] + [^1]: 内容Superscript [1]Numeric footnote, numbered by order of appearance

3.4 Parameters & options

The plugin has no options. The footnote list is appended automatically at the end of the article (<hr> + <section class="footnotes">), and the back-link arrow (↩) on each entry is generated automatically — no need to write it by hand.

3.5 Boundaries & pitfalls

Reference inside a code block / inline codeNot parsed

3.6 Summary

  • Meaningful labels ([^hexo]) are easier to maintain than numbers
  • Pile all definitions at the end; do not scatter them through the body
  • Multiple references to one footnote are fine; back-links are generated automatically

Difference from imgsize.js: markdown-it-imsize is a Markdown rendering plugin that processes the =widthxheight syntax at compile time and writes width/height attributes into <img> tags; the theme also has scripts/events/lib/imgsize.js, which at runtime injects real dimensions into <img> elements without manually specified sizes (synchronous read for local images / asynchronous fetch for remote), preventing CLS. 10.6 Summary

  • Join the two numbers with x; leave the missing one empty: =300x, =x200
  • Percentages need the x: =50%x; a bare =50% breaks the whole image syntax
  • Do not add a title after the size; the plugin does not accept it

⚠️ Known pitfalls

Pitfall 1: Double heading numbering

Symptom: headings render as “1. 1. Overview” (two numbers).

Cause: the theme CSS automatically numbers h2–h6 (on by default), and hand-written numbers (e.g. ## 1. Overview) stack on top.

Fix: pages with hand-written numbering add closeAutoTocNum: true in front-matter; pages without hand-written numbering must not add this field.

This article correctly sets closeAutoTocNum: true.

Pitfall 2: Forgetting the {% raw %}` wrapper **Symptom**: `{% note %}` or `{{ }}` in example source is actually executed or throws a template error. **Fix**: wrap every example code block that contains `{% %}` / `{{ }}` in `{% raw %}` … `{% endraw %}.

Pitfall 3: Config written but not effective

Symptom: link-attributes’ pattern: ^https?:// and mathjax3’s inlineMath are both written, yet the behaviour does not change.

Cause: both are cases of the plugin not recognising that key (one only accepts a matcher function, the other hardcodes $/$$ in its source), so the config silently fails.

Pitfall 4: Config changes require a clean build

Symptom: after modifying markdown.plugins in the root _config.yml (e.g. switching the mathjax/katex engine, enabling multiline), the page does not update.

Cause: Hexo’s cache does not automatically detect configuration changes.

Fix: after changing markdown plugin configuration you must run npm run clean && npm run build.
