This article is both a complete usage tutorial for the matery theme’s layout and page features and an automated testing playground.
Coverage: post layout features, sidebar widgets, responsive breakpoints, galleries, search, comments, dark mode, encryption, RSS/sitemap, PWA.
Automated tests (tools/tests/release-test.sh) assert the rendering markers labeled below.

How to read: every feature shows Effect first (real rendering or behavior), then Corresponding config (the minimal snippet that produces it). When you need a parameter, jump straight to that section’s “All tunable keys” table. Config snippets come from the theme config userConfig/_config.tmp.yml (injected into themes/matery/_config.yml at build time).

4. Content Width Unification (Added 2026-09-07)

Purpose: Make the content column fill the screen without becoming too wide to read.

Learning path: why “ratio + cap” → single vs multi column → width step table → boundaries

4.1 How to enable

Effect: On a 4K screen the content column caps at 1525px (single-column) / 2250px (multi-column), instead of stretching into a 3456px-wide line of text; on FHD it is 1125px / 1250px.

Corresponding config (_variables/base.styl, mixin content-container(wide)):

Design principle: “ratio + cap” — content area width: 90% (relative to the screen) + max-width steps (readability cap). Do not use a pure 90% — at 4K, 90% = 3456px is unreadable.

4.2 Common options

① Standard width for single-column pages

Effect: A single-column wiki page is 1125px on FHD, 1525px on 2K, and still 1525px on 4K (capped).

Corresponding config:

② Wide width for multi-column pages

Effect: A multi-column wiki page’s content column goes from 899px → 1500px at 4K (+67%), on the same step ladder as post-container.

Corresponding config:

Selection rules:

  • Single-column (content without sidebar): content-container() → standard width
  • Multi-column (content + sidebar/TOC): content-container(true) → wide width
  • No hand-written max-width in layouts (always go through the mixin)

4.3 All tunable keys

BreakpointStandard (single-column)Wide (multi-column)
FHD 993-1920px1125px1250px
2K 1921-2560px1525px1750px
4K 2561px+1525px (capped)2250px

4.4 Boundaries & conflicts

  • The step values are hard-coded in the mixin; changing one affects every caller, and an exception for a single page breaks the site-wide visual consistency.
  • Orthogonal to §3 breakpoints: breakpoints decide “how many columns”, this decides “how wide each column is”.
  • The 1525px single-column cap at 4K is deliberate — anything wider makes the eye’s return sweep too long while reading.

4.5 Summary

  • The default single-column is enough: one line, content-container()
  • With sidebar/TOC: content-container(true)
  • Don’t hand-write max-width: layout pages will stop aligning with each other
  • Verification: tools/tests/content-width.test.js (L2m) covers W1 4K wiki==post-container / W3 FHD / W4 2K / W5 single-column capped at 1525px.

Corresponding config (userConfig/_config.tmp.yml, static_prefix.libs section):

Mechanism: Resource URLs carry the version-stamp placeholder {urlVersion}, which tools/cicd.sh replaces at build time via sed with the actual version number (read from tools/.VERSION).

Affected resources:

⚠️ Do not manually edit the {urlVersion} placeholders in themes/matery/_config.yml — that file is a build artifact overwritten by userConfig/_config.tmp.yml during CI.

Client-side language strategy (Scheme A: site-wide follow, 2026-09-10):

Language prefix rules (url_for_lang): Resources (css/js/libs/medias/images/fonts etc.) and static files (xml/txt/json etc.) do not get language prefixes; all other content paths always get the prefix. Exemption rules come from a single source, scripts/utils/url-lang-blacklist.js. Standalone page navigation therefore carries the /en/ prefix pointing to the corresponding language version.

15.4 Boundaries & conflicts

  • Tokens land on :root custom properties through the three-layer chain; components must use var(--*) to follow — hardcoded values never change.
  • font_size_md is rem-based: changing it changes the site-wide size basis, and the preference panel’s --font-scale multiplies on top of it.
  • The mapping lives in the scheme layer source/css/_schemes/matery.styl; renaming a token requires updating the scheme too, otherwise the variable dangles and components get no value.
  • Dark-mode shadows must use the *_dark set; reusing light shadows directly makes them nearly invisible on a dark background.

15.5 Summary

Effect summary: Components reference tokens uniformly (consistent corners/shadows/spacing); changing one place in the design section applies site-wide.

  • Change corners/shadows/spacing: edit the design section, not the components
  • Dark mode needs its own values: *_dark is not optional
  • New components: use var(--*); hardcoding means it won’t follow the theme
  • Testing: CSS contains --font-scale rules and the root font size calc(... * var(--font-scale)).

⚠️ Known Pitfalls

Pitfall 1: Double Section Numbering

Symptom: Headings render as “1. 1. Overview” (two numbers).

Cause: Theme CSS auto-adds numbers to h2–h6 by default; hand-written numbers (e.g. ## 1. Overview) stack on top.

Fix: Pages with hand-written numbering add closeAutoTocNum: true in front-matter; pages without hand-written numbering must not add this field.

This article already correctly sets closeAutoTocNum: true (front-matter line 19).

Pitfall 2: Encryption ↔ TOC Conflict

Symptom: When a wiki is encrypted as a whole, the TOC is hidden by design.

Cause: In encryption mode the TOC component is skipped (intended behavior).

Fix: Test assertions must not hard-code “TOC must exist”. Encrypted wiki pages not showing TOC is normal behavior, not a bug.

Pitfall 3: Wiki English Pages Missing lang: en

Symptom: Sidebar links point to /docs/ instead of /en/docs/.

Cause: wiki_sidebar uses page.lang || default_lang; omitting lang: en falls back to the default language path.

Fix: All pages under source/en/tutorial/ must include lang: en. Verify: for f in source/en/tutorial/**/*.md; do grep -L 'lang: en' "$f"; done.

Pitfall 4: _config.tmp.yml Comment Lines Must Be Preserved

Symptom: Attempted to delete comment lines to slim the file, was vetoed and fully reverted.

Cause: User explicitly declared comment lines are useful reserves (may be restored in the future).

Fix: Never delete or modify comment lines in userConfig/_config.tmp.yml.

Pitfall 5: Config Changes Require Clean Build

Symptom: Changed configuration but the page didn’t update.

Cause: Hexo’s caching mechanism doesn’t auto-detect configuration changes.

Fix: After changing config or source/_data/*, you must run npm run clean && npm run build. Build logs showing INFO Deleted database. and INFO Deleted public folder. confirm clean ran successfully.

Pitfall 6: source/_data/* Incremental Cache Misjudgment

Symptom: After modifying source/_data/friends.yml and other data files, the page is blank or data doesn’t update.

Cause: Hexo’s incremental cache incorrectly judges “cached, unchanged” (Cache hash updated but Data model not written).

Fix:

  • Local: rm -f db.json && npm run build
  • Container: tools/cicd.sh -d (includes clean + generate + config injection)
  • In-container pm2 restart is not enough: pm2 caches old db.json content in memory
