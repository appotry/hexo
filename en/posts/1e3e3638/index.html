This article is a complete tutorial for the matery theme’s automated testing system, paired with the other 4 feature test articles (Content Tags / Interaction & Visual / Layout & Pages / Markdown Syntax) — those 4 are the “test arena”, this one is the “test engine”.
Authoritative sources: tools/tests/release-test.sh (137 lines of pure orchestration) + tools/tests/layers/manifest (the single authoritative 13-layer list), docs/superpowers/specs/2026-08-06-layout-test-cases.md.

How to read: every command shows its Output (what a real terminal looks like) first, then the Corresponding command (the one line that produced it). See an output you want to reproduce — copy the command right below it; want parameters — jump straight to the “Full parameters” table.

1.4 Boundaries & pitfalls

  • Execution order is not documentation order: manifest line order = execution order, and L10 runs first (before L1). Old docs often put L1 on the first line — that is a documentation habit, not the execution fact.
  • A layer script cannot be executed directly: layers/*.sh only defines run_LXX() and depends on release-test.sh having source lib/assert.sh first (pass/fail are global counters). To verify one layer alone, run the test file it wraps, not bash layers/L13_units.sh.
  • A missing layer script is a hard failure: if manifest names a file that layers/ does not contain → ❌ 层脚本缺失：xxx.sh exits 1 immediately, never silently skipped.
  • L13 and L13a overlap: L13 runs “by name” (clear names on failure), L13a “globs unit/** and enforces coverage thresholds”; the same file may run twice — a deliberate double safety net.

1.5 Summary

The layer list lives in exactly one file: tools/tests/layers/manifest. To know “which layers exist and in what order they run”, always read it — not the docs, not a chat log.

3.4 Boundaries & pitfalls

  • L11 always skips locally: --local skips the whole block (⏭️ 跳过 L11 playwright 集成（--local：…）), so “all green locally” does not mean “the browser layer is not broken”.
  • L11 pass criteria are not uniform: some files look for PASS=N FAIL=0, some for 0 失败, and lazyload has no summary line at all (its criterion is “no FAIL/失败/❌”). New files must match the existing criterion, otherwise they go green falsely.
  • L14 retries once automatically on failure: ⚠️ L14 xxx 第 1 次未通过（疑似负载抖动），重试一次…; a retried pass is recorded in the flaky list (see §11) and does not change the PASS/FAIL counts.
  • Unhooked files are now zero: wiki-integration.test.js and infinite-scroll-integration.test.js existed early on but were hooked into no layer; they are now wired in (2026-09-27 / L11 section) with assertions. The only remaining unhooked file is tools/tests/unit-fontawesome.test.py (L13a’s glob only takes .test.js), run it manually with python3 tools/tests/unit-fontawesome.test.py.

3.5 Summary

Layer count is not coverage: L1/L13 answer “does it run”, L2/L7/L8 answer “is it in the artifacts”, L11/L14 answer “is it right in the browser”. Miss one of the three and the fault leaks through the gap.

5.4 Boundaries & pitfalls

  • Retry count/backoff are fixed: 3 attempts, 1s/4s/9s + jitter. Do not raise them “to make it green” — unit-retry.test.sh asserts the backoff library’s behaviour.
  • Do not wrap pure static assertions in retry_match: a local file that cannot be read is not network jitter; retrying only stretches a real bug into 3× the runtime.
  • A retry_match pattern must anchor on zero failures: matching only PASS= turns “4/24 passed” into green (the criterion was tightened on 2026-10-07 because of exactly this).
  • Logs land in /tmp/opencode/: when something goes red, read the file named on the 📄 日志: line — faster than scrolling the terminal.

5.5 Summary

retry_run watches the exit code, retry_match watches the output; both classify only on “all attempts failed” — an intermediate success is flaky: not a failure, but never invisible.

6.3 Full parameters

MechanismDescription
interceptThirdPartyIntercepts known pollution sources (e.g. webpushr returning non-JSON → page unhandled rejection), returns valid JSON instead of aborting (abort produces net::ERR_FAILED, becoming new noise)
collectPageErrorsCollects only JS exceptions + same-origin (localhost/production domain) resource failures; third-party CDN/image-host failures are environment noise and not counted

6.4 Boundaries & pitfalls

  • Do not intercept third parties with route.abort(): abort turns the request into net::ERR_FAILED, adding a same-origin failure — use fulfill to return valid JSON instead.
  • Do not hard-code the baseline domain to production: the second argument of collectPageErrors is the current BASE; running locally while passing the production domain makes local resource failures look like third-party ones and silently disappear.
  • Tests with multiple goto calls must tolerate ERR_ABORTED: otherwise pagination tests go stably false-red.

6.5 Summary

One sentence: same-origin is billed, third-party is not; abort creates noise, fulfill removes it.

7.4 Boundaries & pitfalls

After building, cicd.sh restores _config.yml (only when the changes involve just the minify-switch marker lines), keeping the working tree clean.

  • Do not hand-edit minify in _config.yml to test minification: the next cicd.sh overwrites it per mode, and your manual edit turns into “why did it change again”. Use the flags.

  • The minify switch is only 3 lines: js / css / html. Miss one and you get a half-minified artifact where “JS is minified but CSS is not”.

7.5 Summary

Minification is decided by the build mode, not by the config file; the verification is head -c 200 public/css/main.css — is the first line a single line?

--prepare auto-prepares: starts container if not running, rebuilds if artifacts invalid, rechecks at the end.

Single-instance lock: the gate acquires a lock at ${TMPDIR:-/tmp}/opencode/gate.lock on startup; concurrent runs are rejected outright (prints the lock-holding PID); stale locks are automatically taken over, trap EXIT releases. Concurrent gates are forbidden — they kill each other’s local server.

8.4 Boundaries & pitfalls

  • preflight retries 3 times when the network base is unreachable (❌ 网络基址不可达（HTTP 000，期望 200/301，已重试 3 次）), then prints 💡 检查代理/DNS：curl -sI https://blog.17lai.site — fix the network first, do not touch the assertions.
  • Local mode performs no network base check (only the local 200), so all-green locally does not mean production is reachable.
  • Lock file leftovers: an abnormal exit may leave gate.lock; the script checks whether the PID is alive and takes over automatically — only “a lock holding a live PID” counts as real concurrency.
  • Do not use rm -rf public instead of --prepare: --prepare rebuilds when artifacts are gone, while manual deletion only makes the next gate fail before L1.

8.5 Summary

preflight’s job is “either tell me how to fix it within seconds, or let me through” — it must never let you discover at minute 15 that the server was never up.

  • Four optimizations (2026-09-18~20): critical CSS preload · highlight conditional loading by layout · markmap localized + async · post hero-image preload
  • Threshold: mobile LCP ≤ 2.5s (Search Console “40 URLs over threshold” is the observation basis)
  • Trigger: re-measure whenever head-level resource loading order/conditions change (CSS/JS/images)

13.4 Boundaries & pitfalls

  • Trap: not stripping noscript inflates the resource count by 4 per page (baseline §1.3) — always strip before re-measuring.
  • A single sample is not an acceptance value: under mobile throttling the run-to-run variance is about ±0.9 s; take the median of multiple runs.
  • LCP element identity is unstable: the homepage LCP element drifts between runs, so compare on “element identity + value” together, not the number alone.
  • LCP staying out of the automated gate is deliberate: it needs Lighthouse sampling on real devices with controlled network conditions, which assertion-style tests cannot express.

13.5 Summary

Performance verification = baseline document + reproduction command + median criterion; miss one and any “optimization result” you get is untrustworthy.

Appendix: Triple-Role Self-Check List

When adding or modifying an article in the “hexo theme feature test” series, check these three items:

#CheckPass Criteria
①VerifiableEvery feature has a clear input → expected output (automated assertion marker or manual verification standard)
②DemonstratedEvery feature describes its rendered effect (text description, rendered example, or screenshot)
③ActionableEvery feature has syntax / config steps + caveats (parameter order, prerequisites, common pitfalls)

Quick check: If a feature “only lists its name without saying how to verify” → missing ①; “only lists syntax without showing effect” → missing ②; “doesn’t explain how to use it or is ambiguous” → missing ③.
