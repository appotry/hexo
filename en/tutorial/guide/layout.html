Layout & Pages

This page covers the layout & pages features of the matery theme: post layout features, sidebar widgets, responsive breakpoints, galleries, search, comments, dark mode, encryption, RSS/sitemap and PWA. Each feature lists its config location and how to use it.

Config lives in two places: theme config themes/matery/_config.yml (layout/appearance/interaction) and site config _config.yml (plugins/generators), marked per item below. Note: in this project the theme config file is overwritten by the userConfig/_config.tmp.yml template during CI builds — sync your changes to the template (see the Installation chapter).

How to read this page: every feature is shown as a pair — Effect → Corresponding config. Look at the real page behavior first, then copy the YAML/Stylus below. Defaults come from userConfig/_config.tmp.yml (same source as themes/matery/_config.yml); value sets not present there are marked “other values unverified”.

1.4 Boundaries & conflicts

  • The outdated notice is off by default: outdate.enable: false — unless you turn it on explicitly, no notice appears, which is easily mistaken for a broken feature.
  • toc: false is a string comparison: the template checks theme.toc.enable && page.toc !== 'false', so non-boolean forms (e.g. "False") do not take effect.
  • Ad slots and the TOC share the same sidebar area: many ad entries or a deep TOC make the sidebar visibly longer; on mobile the whole sidebar is hidden, so neither is visible.
  • The copyright card is not the “append copyright on copy” feature: post.copyright controls the end-of-post card, while post.copy.copyright controls the text appended when body content is copied — editing the wrong block has no effect.

1.5 Summary

  • All five modules are single-line switches in the theme config; all are on by default except the outdated notice.
  • Per-post granularity only has two override points: toc and reprintPolicy.
  • After changing theme config you must run hexo clean && hexo generate; in CI also sync userConfig/_config.tmp.yml.

  • To change appearance you must edit CSS/templates; config cannot do it.

  • Breakpoint variables are referenced by many styl files; changing them affects nav, sidebar, grid and effects at once — the “change only one place” expectation does not hold.

  • $breakpoint-fun only controls effects; it does not affect the layout column count.

3.5 Summary

  • Five breakpoints + two width tiers make up all responsive behavior.
  • Width priority: standard for single-column, wide for multi-column, decided uniformly by the mixin.

Corresponding config (top-level search.default):

  • search.default (value algolia / local / pagefind) selects the default engine; if the configured default is not enabled, the front end auto-degrades to the first enabled engine and logs a console.warn.
  • The Algolia client (algoliasearch) is lazy-loaded: it is injected only when the search popup opens, not preloaded site-wide.

In-page engine switching and keyboard shortcuts

(Source: themes/matery/layout/_partial/common/search.ejs, _partial/script/search.ejs)

Effect: you can switch engines inside the popup and it re-searches immediately; the next open remembers your last choice; Ctrl+K opens it at any time.

Corresponding config: none (built-in behavior). Key points:

  • The popup’s left-side engine icon #searchEngineBtn opens a dropdown #searchEngineMenu to switch between local / algolia / pagefind; the dropdown button auto-hides when at most one engine is available.
  • Results render in real time for the current engine; switching triggers an immediate re-search with the current input value; the active engine is persisted in localStorage (key search_engine).
  • Ctrl+K / Cmd+K opens the search popup, Esc closes the menu; the popup uses the native popover and light-dismisses on outside clicks.
  • IME compatibility: input events skip IME composition mid-states; compositionend falls back to searching with the full value (shared by all three engines).

Multilingual filtering and unified highlighting

(Source: themes/matery/source/js/search.js)

Effect: multilingual versions of the same document don’t flood the results — only the user’s preferred language remains; keywords are safely highlighted in results and on the target page.

Corresponding config: none (built-in behavior). Key points:

  • Multilingual filtering: all three engines share applyLangFilter() — results are grouped by path language prefix, the entry matching the user’s preferred language (localStorage key wiki_lang, language list from window.MATERY_LANG.langs) is returned first, missing entries fall back to the default language (default_lang), duplicates within a group are removed.
  • Unified highlighting: all three engines share the base class _highlight() — keywords are escaped then wrapped in paired <mark class="search-keyword"> tags (prevents XSS / unclosed tags); highlight HTML returned by Algolia is stripped by _safeHighlight() and re-highlighted locally.
  • Jump-to-page highlighting: result links append ?highlight=<keyword>; the post page’s search.ejs tail script parses the parameter and highlights body text (skipping code blocks and links).

Pagefind build steps

Effect: public/pagefind/ holds a static index; search works client-side with no external service.

Corresponding config (scan public/ after hexo generate and before deployment; runs in the CI phase, see tools/CI.sh):

The locally installed version is preferred; if not present, the pinned version pagefind@1.5.2 is downloaded once (prevents npx from pulling a floating latest).

5.4 Boundaries & conflicts

  • preload / trigger are configured but unimplemented keys: setting them changes nothing; the index is always fetched when the popup first opens.
  • Algolia has a hard 10KB per-record limit: an overlong body is rejected by the service (HTTP 400) and must be truncated via content_length; Chinese counts ~3 bytes per character, so the limit is much lower than for English.
  • output_subdir must not start with an underscore: GitHub Pages (Jekyll) ignores directories starting with _, so the index is simply not published.
  • Pagefind must run after hexo generate: reversing the order scans stale artifacts or an empty directory.
  • Enabling all three engines at once lets their configs mask each other’s problems: when debugging search issues, keep only one engine enabled first.

5.5 Summary

  • The three engines are independent; search.default picks the preferred one and auto-degrades when it is not enabled.
  • local and Pagefind are both purely static; Algolia needs an extra index push.
  • field / content / content_length are the three main knobs controlling index size.

8.4 Boundaries & conflicts

  • enable: false makes already-encrypted content unreadable: the ciphertext assets remain, but the front end no longer loads the decryption logic — the result is a blank area or raw ciphertext. Re-enabling restores it.
  • autoSave is convenience and risk: the decryption key is cached in localStorage (1 day), which on a shared device means one day without a password.
  • The wiki password and post passwords are independent: after changing a wiki’s encrypt_password, browsers that already unlocked it can still read old pages with the old key (within the TTL).
  • The hexo-blog-encrypt plugin is deprecated: only this theme’s encrypt section is read; configuring per the old plugin docs has no effect.
  • Missing one raw tag in snippet encryption causes an unknown block tag error at build time (the examples on this page already include it).
  • Asset minification (2026-09-25): hbe encryption assets now live in source/libs/hbe/ and go through the static pipeline, so hexo-minify compresses them (previously bypassed).

8.5 Summary

  • Four granularities: tag bulk, per-post, snippet, whole wiki.
  • Everything decrypts on the front end — it guards against casual access, not server-side authorization: both ciphertext and key-derivation parameters live in the page.
  • Wiki unlock state is shared across pages with a 1-day TTL.

10.2 Common options

SW version management details

(Source: userConfig/sw.tmp.js, themes/matery/layout/_partial/common/head.ejs, tools/cicd.sh)

Effect: after a new deployment, users need no manual refresh and are not interrupted by popups; old caches are cleaned up automatically.

Corresponding config: none (CI and templates cooperate). Key points:

  • Template → artifact: during CI, tools/cicd.sh’s inject_pwa_sw() first copies userConfig/sw.tmp.js to source/sw.js, then injects placeholders with sed; the artifact is published as /sw.js at the site root.
  • Cache key / version injection: the template uses the literal 17lai-cache-{uniqueIdentifier} as the cache key (prefix 17lai-cache-); CI replaces the placeholder with a build timestamp (date '+%Y%m%d%H%M%S', i.e. offline_version), producing a unique key like 17lai-cache-20260913181700 — a new version on every build. The same step also injects {cdnUrl} / {cdnPathVersion} / {cdnPathLatest} / {urlVersion} placeholders.
  • Client auto-refresh once (head.ejs, registered as an async script when theme.pwa.enable is true, scope: '/'; skipped on localhost to avoid stale-cache hits during local development):
    1. After registration, sends a checkIdentifier message to the SW via MessageChannel, retrieves the current cache version, and records the baseline.
    2. On updatefound → new SW installed (after pre-cache addAll completes), and on controllerchange (SW takes over), triggers checkVersionAndRefresh().
    3. Only reloads (window.location.reload(), delayed 500ms for activate to finish) when the cache version changes; a refreshed guard ensures one reload per page, preventing Vercel redeploy-triggered reload loops — no popup, no manual refresh.
  • Activation and old-cache cleanup (SW template): the install event pre-caches cacheList then calls self.skipWaiting(); the activate event iterates caches.keys(), deletes old caches with the 17lai-cache- prefix that don’t match the current cache key, re-runs addAll, then calls self.clients.claim() to take over all pages.
  • Minified backup: in release mode the uncompressed sw.js is backed up to userConfig/sw.js; after the build, the minified version is backed up to userConfig/sw.min.js. Continue mode reuses sw.min.js to keep minified artifacts consistent (falls back to the template version if missing).

10.3 All tunable keys

Key / fileTypeDefaultAllowed values / rangeEffect
pwa.enablebooltruetrue / falseRegister the SW and manifest

{uniqueIdentifier}placeholderbuild timestampYYYYMMDDHHMMSSCache key, changes every build

10.4 Boundaries & conflicts

  • SW caching is the most common cause of “changes don’t apply”: localhost skips registration, but visiting the test domain by hostname hits the old cache — unregister the SW / clear site data before debugging.
  • An unchanged version does not trigger an update: changing content without rebuilding (or reusing the old version with -c) keeps the same cache key, so clients may keep the old cache.
  • If template placeholders are not injected (running hexo generate locally), {cdnUrl} etc. stay as literals in sw.js, causing cache requests to 404.
  • Skipping registration on localhost is intentional — don’t debug “why is there no SW” locally.

10.5 Summary

  • PWA has only one switch; the real complexity is the version-injection chain in sw.tmp.js.
  • Cache key = build timestamp, so “every deployment is a new version”.
