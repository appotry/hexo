Deployment

This page explains the blog’s release & deployment: how static output is hosted, the Vercel production deployment and test-domain flow, the four Docker build modes, and the “code change vs content change” release choice. The deployment chain relies on git submodules (themes/matery/ etc.), so commits need both repos committed together (see section 6).

How to read: every deployment target is given as a pair — Effect (which domain/repo gets updated) → Corresponding command/config → Output. Config sections still follow “How to enable → Common options → All tunable keys → Boundaries & conflicts”.

1. Deploying Static Output (any static host)

Purpose: Hexo generates pure static files; the public/ directory can be dropped on any static host (Nginx, GitHub Pages, Cloudflare Pages, OSS etc.) and go live directly.

Effect: public/ contains the complete site (index.html + page directories + static assets); sync it to any web server root and visiting that domain shows your blog.

1.4 Boundaries & conflicts

  • Deploying means syncing public/: copy it to the web server root and you’re done; where the domain points is decided by the hosting platform.
  • The root URL must match: url in _config.yml decides absolute links in canonical/sitemap/RSS — change it when the hosting domain changes (see the Global Configuration chapter).
  • This project uses Vercel in production (next section); the old GitHub Pages deployment is retired.

1.5 Summary

  • Minimum viable: npm run build, then sync public/
  • Changing domain: update url in _config.yml first, then build
  • Local viewing only: npx hexo server -p 4100

2. Vercel Production Deployment (blog.17lai.site)

Purpose: production at https://blog.17lai.site. Vercel is linked to the GitHub repo github.com:appotry/hexo.git (main branch) — pushes trigger automatic builds, no manual trigger needed.

Learning path: How to enable → Common options → All tunable keys → Boundaries & conflicts

2.1 How to enable

Effect: the main branch of hexo.git gains one commit + one git tag; minutes later https://blog.17lai.site becomes the new version and the ?v= version in the HTML increments (so browsers/PWA fetch the new assets).

Corresponding command:

Output:

  • tools/.VERSION increments and the matching git tag is created
  • Only hexo.git (production) is pushed; hexoback.git is untouched
  • Vercel runs npm run build in the cloud and the output goes straight onto the CDN

2.2 Common options

① Verify production after release

Effect: layer-by-layer checks against the production domain — complete build output, 20 layout pages returning HTTP 200, comment sections present, version consistent in three places, SW smoke, etc.; any failing layer errors out.

Corresponding command:

Output: a PASS/FAIL report per layer L1–L14 with a final total; the release only counts as done when everything is green.

② Don’t create an extra deployment repo

Effect: production only trusts hexo.git, and Vercel only watches it; a second repo means two sets of output and a confused domain mapping.

Corresponding config: the Vercel project’s Git integration (in the Vercel console, not repo config).

2.3 All tunable keys

Deployment targetTriggerRepoResulting domain
Productiontools/cicd.sh -r "feature"hexo.git (main)https://blog.17lai.site
Test domaintools/cicd.sh -t "desc"hexoback.githttps://blog2.17lai.site
Content onlytools/cicd.sh -c "desc"hexo.git + hexoback.gitboth domains update
Local debuggingtools/cicd.sh -dno pushlocal preview only

2.4 Boundaries & conflicts

  • The build runs on Vercel’s cloud (npm run build), with output going straight onto the CDN; a successful local build doesn’t mean the cloud build succeeds — the Vercel build log is authoritative.
  • Don’t create a deployment repo besides the production one; testing uses the independent hexoback.git (next section).
  • After release, run tools/tests/release-test.sh per the release rule to verify production (20 pages + comment sections + version consistency).

2.5 Summary

  • Minimum viable: tools/cicd.sh -r "desc"
  • Must verify after release: tools/tests/release-test.sh
  • Broke production: revert to the previous git tag, then -r again
  • Content only: use -c, no version bump

3. Test Domain Flow (hexoback → blog2.17lai.site)

Purpose: verify on the test domain before a real release, keeping broken changes off production. Vercel has a second project listening on hexoback.git (test repo), deploying to https://blog2.17lai.site.

Learning path: How to enable → Common options → All tunable keys → Boundaries & conflicts

3.1 How to enable

Effect: hexoback.git updates → https://blog2.17lai.site becomes the new version; production blog.17lai.site is completely unchanged.

Corresponding command:

Output: -t switches the deploy target to hexoback only and pushes; make test-pwa prints SW smoke results for 7 pages plus interaction findings.

3.2 Common options

① Push production only after tests pass

Effect: the production domain updates with the same output as the test domain, carrying the bumped version number.

Corresponding command:

Output: hexo.git gains a commit and tag; release-test.sh prints L1–L14 results.

② Skip the test domain for small changes

Effect: when only content changes, push to both (production + test) directly, saving one wait.

Corresponding command:

Output: both hexo.git and hexoback.git update, with the version number unchanged.

3.3 All tunable keys

RepoWatched byCommandResult
hexo.gitVercel production project-r / -cblog.17lai.site
hexoback.gitVercel test project-t / -cblog2.17lai.site

3.4 Boundaries & conflicts

  • The two repos are fully separate, so testing never pollutes production; but -t reuses the old version, so it does not create a new tag.
  • make test-pwa targets the test domain (blog2.17lai.site), not local port 4000.
  • Small changes (content only) can skip the test domain and push directly with -c.

3.5 Summary

  • Minimum viable: -t → make test-pwa
  • After it passes: -r → release-test.sh
  • Posts only: -c
  • Test-domain error: fix it and re-run -t — never go straight to production

4.1 How to enable

Effect: after running -d inside the container, localhost:4000 shows the real posts + unminified + no CDN debug build; config injection and PWA generation still run, but nothing is pushed to any repo.

4.4 Boundaries & conflicts

  • The hexo server inside the Docker container maps port host 4000 → container 4000; for local preview use tools/test.sh server or npx hexo server -p 4100 — the two don’t conflict.
  • Post-set replacement has been moved out of cicd.sh (2026-09-23): to speed things up with a small debug post set, run tools/debugBlog.sh true first, then tools/cicd.sh -d; restore with tools/debugBlog.sh false when done. Build scripts shouldn’t modify source files.
  • -d doesn’t push, but it does rewrite themes/matery/_config.yml (the config injection output); that’s expected — don’t commit it as a dirty change.

4.5 Summary

  • Minimum viable: tools/cicd.sh -d + open port 4000
  • Needs pushing: -c (both) / -t (test) / -r (production)
  • Port conflict: use 4100 for local preview
  • Faster builds: debugBlog.sh true is a separate step

5. Release Flow Selection (code vs content)

Purpose: picking the wrong mode means “changed it but production didn’t move” (cache hit on the old version) or an unnecessary version bump.

Learning path: How to enable → Common options → All tunable keys → Boundaries & conflicts

5.1 How to enable

Effect: git status --short prints themes/matery/ → code change → must use -r; only source/ prints → content change → -c/-d is enough.

Corresponding command:

Output: lists the changed files; empty output means nothing changed in that directory.

5.2 Common options

Core principle: code changes use -r, content changes use -c/-d.

Change typeCommandReason
JS/CSS/theme code (under themes/matery/)tools/cicd.sh -r "feature"needs a version bump + git tag so browsers/PWA fetch the new version (unchanged version = cache hit)
Posts/content only (source/_posts/ etc.)-d (local preview) or -c "desc" (push)content updates need no version, incremental release
Changing the JS version numbermust -r (bump in 3 places, then release)otherwise production serves the cached old version

5.3 All tunable keys

ModeVersion behaviourHow to observe
-rreads tools/.VERSION, bumps it and creates a git taggit tag gains one; the page’s ?v= grows
-creuses the old versiontools/.VERSION unchanged

5.4 Boundaries & conflicts

  • The version number is synced in 3 places (tools/.VERSION, {urlVersion} in userConfig/_config.tmp.yml, userConfig/sw.tmp.js); miss one and part of the assets stays cached.
  • Using -r for a content-only change needlessly bumps the version and makes every visitor re-download static assets.

5.5 Summary

  • Theme code changes: -r
  • Post changes: -c (push) or -d (preview)
  • Unsure: run git status --short first to see which directory changed

6. Dual-Repo Commits (submodules)

Purpose: the theme lives in the submodule themes/matery/; after theme changes both repos must be committed, otherwise the parent repo still points at the old commit.

Learning path: How to enable → Common options → All tunable keys → Boundaries & conflicts

6.1 How to enable

Effect: the submodule repo gains one commit and the parent repo gains an “update submodule pointer” commit; the parent’s git status no longer shows themes/matery as modified.

Corresponding command:

Output: two commit calls produce one commit each; git status is clean.

6.2 Common options

Local commit convention: [emoji] type(scope): description, one commit does one thing.

typeemojiPurpose
feat✨new feature
fix🐛bug fix
docs📖documentation
refactor♻️refactoring
perf⚡performance
test🧪tests
chore🔧build/tooling/config
style🎨formatting

6.3 All tunable keys

RepoPathWhat’s committed
Submodulethemes/matery/theme code changes
Parent reporepo rootsubmodule pointer + site content/scripts

6.4 Boundaries & conflicts

  • Committing only the parent without the submodule → the parent pointer still points at the old commit, and the theme change never reaches production.
  • The two repos have different remotes (gitea is the main one); check each remote when pushing.

6.5 Summary

  • Minimum viable: submodule commit → parent repo pointer commit
  • Forgot step two: the parent’s git status keeps showing the submodule as modified
  • Commit message: [emoji] type(scope): description
