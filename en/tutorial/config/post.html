Post Page Configuration

This page explains the post page configuration: hero image, meta info under the title (date/word count/reading time/views), TOC, comments, reward, copyright, math and diagrams. Everything lives in the post section of the theme config.

The authoritative source of the theme config is userConfig/_config.tmp.yml (it overwrites the theme config at CI time).

How to read: every section follows “How to enable → Common options → All tunable keys → Boundaries & conflicts”. Look at the effect first, then the corresponding config that produces it — copy and use.

Display & Layout

1. Post Page Hero Image

Purpose: the banner at the top of post pages (distinct from the homepage hero; it can be set independently).

Learning path: How to enable → Common options → All tunable keys → Boundaries & conflicts

1.1 How to enable

Effect: open any post and a full-width hero image appears at the top, taking 70% of the viewport height, with a 30% black mask on top to raise the contrast of the white title.

Corresponding config (theme config, post section):

1.2 Common options

① Change the hero image for one post

Effect: only that post’s top image is replaced; other posts keep the global hero.

Corresponding config (post front-matter):

② Adjust the hero height

Effect: the larger the value, the taller the hero and the further the title moves down; 70 takes about seven tenths of the viewport, 40 leaves only a strip.

Corresponding config:

③ Adjust the mask darkness

Effect: 0 applies no darkening (white text may be unreadable on a light image), 0.5 darkens noticeably, 1 is fully black.

Corresponding config:

④ Auto-pick an image when front-matter has none

Effect: when a post has no img, one image is picked deterministically from the featureImages array by a hash of the title — the same title always gets the same image.

Corresponding config (theme config, top-level featureImages):

1.3 All tunable keys

KeyTypeDefaultAllowed values / rangeWhat it does

1.4 Boundaries & conflicts

Hero image source priority (_partial/post/post-cover rendering logic):

  1. front-matter img (e.g. img: /medias_webp/xxx.webp) — explicit
  2. without img, pick one from theme.featureImages by a hash of the title (/medias_webp/featureimages/0-44.webp; the same title always gets the same image)
  3. when random background is on (theme.background.image.random), the post banner is hidden

Note: featureImages only sources from medias_webp/featureimages/ (webp, numbered 0-44, with a dark/ subdirectory); the legacy medias/featureimages/ (jpg) is removed — do not reference .jpg paths.

1.5 Summary

  • Minimum: write banner_img alone and the hero appears
  • Make the title stand out: raise banner_mask_alpha, or lower banner_img_height
  • Specialize one post: write img / banner_img in its front-matter, leave the global alone
  • Change has no effect: the hero path is an asset change — a clean build is required

2. Meta (meta)

Purpose: the info row under the post title: date, word count, reading time, views — each independently toggleable.

Learning path: How to enable → Common options → All tunable keys → Boundaries & conflicts

2.1 How to enable

Effect: a row of small grey text appears right under the post title, e.g. “2026-08-07 · 2,345 words · 8 min · 123 views”. With only date and word count enabled, the row shrinks to “date · word count”.

Corresponding config (theme config, post.meta section):

2.2 Common options

① Date and format

Effect: shows the post date. "LL a" outputs a localized form such as “August 7, 2026 Friday”.

Corresponding config:

② Word count

Effect: “N words” appears under the title; CJK text is counted per character.

Corresponding config:

③ Reading time

Effect: an “N min” estimate appears. A larger wpm estimates shorter; awl is the average word length factor — keep it at 1 for CJK.

Corresponding config:

④ Views

Effect: “N views” appears. Where the number comes from is decided by source — switching data sources changes only this one value.

Corresponding config:

⑤ Author

Effect: the author name appears under the title. Off by default; when on it prefers front-matter author, falling back to the site author.

Corresponding config:

2.4 Boundaries & conflicts

  • post.meta.views.source decides where views come from — this blog uses umami (self-hosted analytics); you can also switch to busuanzi (zero config) or Waline comment views.
  • Choosing leancloud also requires the leancloud_visitors config from §21; choosing waline requires waline.pageview: true.
  • post.meta and §11 postInfo are two independent mechanisms — enabling both shows the info twice on the page, so keep only one as needed.

2.5 Summary

  • Minimum: date.enable + wordcount.enable
  • Fewer requests: use umami for views, don’t enable leancloud_visitors at the same time
  • Reading time is off: tune wpm (250–350 for CJK)
  • Don’t duplicate postInfo: first check whether the info bar already shows it

Corresponding config:

② Collapse depth

Effect: 0 collapses everything, showing only top-level entries; a value greater than 0 expands entries that have children by default.

Corresponding config:

③ Disable for one post

Effect: that post shows no TOC; other posts are unaffected.

Corresponding config (post front-matter):

4.4 Boundaries & conflicts

  • collapseDepth of 0 means fully collapsed; >0 expands entries that have children by default.
  • Headings must be produced by Markdown ##/### for the TOC to pick them up; hand-written HTML headings need the matching class/selector.
  • toc: false on a single post only hides the TOC — it does not affect heading rendering in the body.

4.5 Summary

  • Minimum: toc.enable: true
  • TOC too long: narrow headingSelector
  • Want it expanded: collapseDepth: 2
  • No TOC on one post: front-matter toc: false

5.4 Boundaries & conflicts

  • Whichever engine type points to, you must also configure that plugin’s required params (e.g. this blog’s waline.serverURL). Page-level control uses front-matter comments: true/false (same for standalone pages, message pages and friends pages).
  • Valine-specific keys have no effect under Waline (waline.ejs does not read them).

  • Gitalk/Gitment OAuth permissions are too broad — utterances/giscus are preferred.

5.5 Summary

  • Want GitHub comments: giscus, fill in the 4 ids
  • Dark mode looks wrong: check the waline.dark selector
  • No comments on one page: front-matter comments: false

Info Display

Post front-matter (in-house HBE v4 since 2026-08-09; the password is plaintext, a SHA256 hash is no longer required):

17.4 Boundaries & conflicts

  • In-house HBE v4 (AES-256-GCM, replacing hexo-blog-encrypt since 2026-08-09) — server-side AES-256-GCM encryption stores ciphertext in HTML (no plaintext leakage), front-end WebCrypto decryption. Write the plaintext password directly in front-matter password (no SHA256 pre-hashing needed).
  • Other encryption methods:
    • Content snippet encryption: {% encrypt password "title" "abstract" %}...{% endencrypt %} (paragraph-level, supports nested tags, see the Tag Plugins chapter §15)
    • Wiki-wide encryption: add encrypt_password to {wiki}-sidebar.yml (see the Layout & Pages chapter §8)
    • Password storage: autoSave stores the derived DK (not the password/plaintext), 1-day TTL
  • Refresh after decryption (2026-09-09): once decryption finishes, components in the body are re-initialized uniformly (shared by post/wiki/gallery, triggered by hbe-bundle onSuccess) — code block toolbar (codeWidget), image lightbox (articleInit), mermaid/progress bars (events.refresh), layout (boot.refresh). No manual page refresh is needed; each component is idempotent (data-processed prevents duplication).

17.5 Summary

  • Minimum: verifyPassword.enable + front-matter password
  • Hide only one paragraph: use the encrypt tag instead of encrypting the whole post
  • Encrypt a whole section: encrypt_password in {wiki}-sidebar.yml
  • Password is plaintext: HBE v4 no longer needs SHA256
