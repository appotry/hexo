本文既是 matery 主题布局与页面功能的完整使用教程，也是 自动化测试靶场。覆盖：文章布局特性、侧边栏组件、响应式断点、相册、搜索、评论、暗色模式、加密、RSS/站点地图、PWA。自动化测试（tools/tests/release-test.sh）会断言下方标注的渲染标记。

阅读方式：每个功能都先看 效果（真实渲染或行为描述），再看 对应配置（产出该效果的最小片段），需要查参数时直接跳到该节的「全部可调项」表。配置片段来自主题配置 userConfig/_config.tmp.yml（构建时注入 themes/matery/_config.yml）。

1.7 更新时间（更新于）

效果：文章头部显示「更新于 2026年9月26日 上午」（各篇不同）；从未改动过的文章不显示该行 —— 由 compare_date(page.date, page.updated) 守卫：两个时间相等时不出这一行。

数据来源（2026-09-26 修复）：取文章源文件在 git 中的最后提交时间 —— 既不是文件 mtime，也不等于发布时间。

候选来源为何不用
文件 mtime会被 git checkout/clone/批量脚本重置（实测 142 篇 _posts 的 mtime 全落在同一秒）→ 全站显示同一天
date（发布时间）无法反映修改，出现「更新于 == 发布于」
git 提交时间 ✅提交时固化，不受工作树任何操作影响

常用选项：

① 相对时间

效果：「更新于 3 天前」而非「更新于 2026年9月26日 上午」。

对应配置：

② 作者手动指定

效果：该篇显示 front-matter 写的日期，不再用 git 时间。

对应配置（front-matter）：

实现：scripts/filters/post-updated.js 在 before_generate（早于全部 generator）用 scripts/utils/git-time.js 读到的 git 时间覆盖 post.updated；作者在 front-matter 写 updated: 时以作者值为准。

测试断言：tools/tests/unit/unit-updated.test.js（4 用例：中文路径命中 / 不存在返回 null / 未显式指定被覆盖且为 moment / 作者显式值保留）；文章页含 datetime="…" update。

4. 内容宽度统一（2026-09-07 新增）

用途：让正文列在不同屏幕上既铺满又不至于宽到读不下去。

学习路径：为什么要"比例+上限" → 单栏/多栏怎么选 → 宽度阶梯表 → 边界

4.1 如何启用

效果：4K 屏上正文列封顶 1525px（单栏）/ 2250px（多栏），不会拉成 3456px 宽的一行字；FHD 上则是 1125px / 1250px。

对应配置（_variables/base.styl，mixin content-container(wide)）：

设计原则：“比例 + 上限”——内容区 width: 90%（相对屏幕）+ max-width 阶梯（可读性上限）。不要纯 90%——4K 下 90% = 3456px 不可读。

① 单栏页面用标准宽度

效果：wiki 单栏页在 FHD 上 1125px、2K 上 1525px、4K 仍 1525px（封顶）。

对应配置：

② 多栏页面用宽宽度

效果：wiki（多栏）4K 内容列 899px → 1500px（+67%），与 post-container 同宽阶梯。

对应配置：

选型规则：

  • 单栏（内容无侧栏）：content-container() → 标准宽度
  • 多栏（内容 + 侧栏/TOC）：content-container(true) → 宽宽度
  • 禁止 layout 手写 max-width（统一走 mixin）

15.4 边界与冲突

  • 令牌经三层链落到 :root 自定义属性，组件必须用 var(--*) 才跟随；硬编码值不会变。
  • font_size_md 是 rem：改它等于改全站字号基准，偏好面板的 --font-scale 会在其上再乘一次。
  • 映射在方案层 source/css/_schemes/matery.styl；改令牌名要同步改 scheme，否则变量悬空、组件拿不到值。
  • 暗色阴影必须用 *_dark 那一套；直接复用亮色阴影在深底上几乎看不见。

15.5 小结

效果汇总：组件统一引用令牌（圆角/阴影/间距一致），改 design 段一处即全站生效。

  • 改圆角/阴影/间距：改 design 段，别去组件里改
  • 暗色要单独给值：*_dark 不能省
  • 新组件：var(--*)，硬编码就不跟随主题
  • 测试：CSS 含 --font-scale 规则与根字号 calc(... * var(--font-scale))。

⚠️ 已知坑

坑 1：标题编号双重叠加

现象：标题渲染为「1. 1. 概述」（两个编号）。

原因：主题 CSS 自动给 h2–h6 加编号（默认开启），手写编号（如 ## 1. 概述）会叠加。

正确做法：手写编号的页面在 front-matter 加 closeAutoTocNum: true；不手写编号的页面不要加该字段。

本文已正确设置 closeAutoTocNum: true（front-matter 第 19 行）。

坑 2：加密 ↔ TOC 冲突

现象：wiki 整体加密时 TOC 按设计不显示。

原因：加密模式下 TOC 组件被跳过（设计如此）。

正确做法：相关测试断言勿写死「TOC 必须存在」。加密 wiki 页面不显示 TOC 是正常行为，不是 bug。

坑 3：Wiki 英文页漏 lang: en

现象：侧栏链接指向 /docs/ 而非 /en/docs/。

原因：wiki_sidebar 使用 page.lang || default_lang，省略 lang: en 则回落到默认语言路径。

正确做法：所有 source/en/tutorial/ 下的页面必须写 lang: en。验证：for f in source/en/tutorial/**/*.md; do grep -L 'lang: en' "$f"; done。

坑 4：_config.tmp.yml 注释行保留

现象：尝试删除注释行瘦身，被用户否决并 100% 回滚。

原因：用户明确声明注释行是有用储备（未来可能恢复）。

正确做法：永远不要删除或修改 userConfig/_config.tmp.yml 中的注释行。

坑 5：改配置后必须 clean 构建

现象：改了配置但页面不变。

原因：Hexo 缓存机制不会自动检测配置变更。

正确做法：改配置或 source/_data/* 后必须 npm run clean && npm run build。构建日志中出现 INFO Deleted database. 和 INFO Deleted public folder. 表示 clean 成功执行。

坑 6：source/_data/* 增量缓存误判

现象：修改 source/_data/friends.yml 等数据文件后，页面空白或数据不更新。

原因：Hexo 增量缓存误判「已缓存未变化」（Cache 哈希更新但 Data model 未写入）。

正确做法：

  • 本地：rm -f db.json && npm run build
  • 容器：tools/cicd.sh -d（内置 clean + generate + 配置注入）
  • 容器内 pm2 restart 不够：pm2 内存缓存 db.json 旧 content
